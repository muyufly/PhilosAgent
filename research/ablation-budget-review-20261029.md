## 新增预算的含义

“追加同样七条预算”以原 v2 中 **恰好七条 `status=complete` 的原运行实测用量**作为新增额度参考。这七条是：engineering 的 `p0phi0` 三次重复、`p0phi1` 三次重复，以及 `p1phi0-r00`。它们与上表七格主矩阵不是同一组运行。

| 新增额度指标 | 阈值 |
|---|---:|
| Chat total tokens | 14,220,327 |
| SDK Chat 请求 | 2,666 |
| DeepSeek 搜索／抓取请求 | 1,616 |
| 其中：搜索／抓取的历史组成 | 966／650 |

历史参考 Chat tokens 中，输入为 13,460,241，输出为 760,086；七条的 2,666 个 SDK 请求均有成功状态和 usage。工具请求包含失败的 HTTP 尝试，不能只把 HTTP 200 计入新增请求预算。

三个阈值用于限制**新范围启动后的追加用量**，不能把旧审计前缀再次算入新增消耗，也不能在启动器重启后清零。任何一项耗尽都应阻止新的 Chat 和工具请求；失败尝试也占用请求次数。响应缺失 usage、超时或其他无法确认 token 用量的请求应记录为未知，不能按零消耗继续放行。

这是 token／请求计数止损规则，**不是已确认的金额上限**。总 tokens 在响应返回后才能准确记账，因此阈值到达前已经放行的少量在途请求可能使最终 tokens 超出阈值。两条运行内部还可能有原生并行比较；“两条运行并发”不能直接解释为“最多两个 API 请求在途”。应公开账本中的在途和最终增量，而非承诺绝对不超额。

## 配额中断的结果语义

预算启动器只增加独立的范围控制和计量，不修改已固定的 `philoagent`／vendor 实验源码、提示或选优算法。请求名额需在实际发出前以共享账本原子预占，返回后累计实际 tokens。

配额拒绝是实验中断，**不是候选质量差、答题错误或父代胜出**。即使原生代码捕获了异常并返回父代，启动器也必须检查本次运行是否发生过配额拒绝／用量未知：发生后不得将该运行发布为 `complete`，不得把该运行分数纳入完成结果。保留已执行前缀和中断原因，不自动重试。只有完成两轮、全部锁定留出任务及原有完整性检查，且没有预算拒绝，才允许作为本次新完成结果汇总。

## 这七格能回答的问题

engineering 的四格允许描述 P、Φ 的条件效应与二者交互。其余三种初始条件只有联合演化格，可与 engineering 联合演化格比较初始化条件下的观察结果，但不能分别归因于 P 或 Φ。

因此，这是**带预算约束的七格探索性比较**，不是四种初始条件各自完整的因子消融，也不再是原 48 条、三重复完整实验。主比较只使用固定的 `r00`；其他已经完成的 engineering 重复可作补充材料，不能混入主比较后将不同种子的重复数视为相同。

共同留出集仅四个独立任务。重复次数、API 请求数量或候选代码变化都不能替代独立任务数量，也不能单独证明某种哲学更优或性能获得稳定提升。预算阈值可能先于矩阵完成触发；此时应报告已完成与被中断的格，不补零、不挑选替代重复、不声称七格已经完成。
